## 本轮实施建议

| 重排 | Qwen/Qwen3-Reranker-0.6B | 使用官方 query/document 模板及 yes/no logits 评分；不是让聊天模型自由生成排序 |

两个 Qwen 的模型仓库与规格见 [Embedding 官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)、[Reranker 官方模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)。Embedding 的0.6B版本支持1024维，和当前存储维度一致；维度一致不代表向量空间兼容。

DeepSeek 的 chat/sql 可以指向同一地址、同一模型，分别使用独立能力配置、任务上下文和用量统计；密钥可以由同一后端环境变量引用，无需为同一账户复制密钥正文。供应商账户额度和限流应合并计算，不能只靠当前每能力/每进程信号量当作全局限流。

## 本机部署与资源建议

本轮 `nvidia-smi` 实测：NVIDIA GeForce RTX 3060 Laptop GPU，6144 MiB，驱动610.74；采样时已用显存0 MiB。这是硬件快照，不是模型运行结果。

以项目内隔离的 Python 推理环境运行一个本机模型服务进程，提供 Embedding 和 Rerank 两个接口；权重使用获准共享目录，数据库继续在既有 Debian Docker，主客服/临时 SQL 调远端 API。不改变现有数据库部署。

- 使用 PyTorch＋Transformers 的原生推理路径，先FP16、eval/inference模式；精确版本以安装兼容和回归结果锁定。权重放获准shared-models快照，运行缓存和依赖留在01，记录HF提交修订与文件摘要。
- 两模型FP16权重合计约2.4GB（0.6B×2模型×2字节的估算），尚未包含CUDA上下文、激活、临时张量和其他进程。两模型常驻必须实测，不能据此承诺6GB足够所有负载。
- 起始建议：单进程共享GPU执行队列，并发1；Embedding微批4、重排微批1，最大编码长度先1024 tokens，混合召回后最多20条进入重排、返回前5条。这些是待测初值，不替代已批准的质量/时延门槛。原HTTP接口上限与GPU微批不同，可把一批请求拆成多个微批。
- 知识索引任务与在线检索共享资源，在线请求优先，队列有界并计入超时；避免导入占满GPU。长文先沿既有切分链路处理，不静默截去业务依据。若显存不足，依次减微批/编码长度，并用留出集复核；必要时采用CPU重排并标记性能状态，不把OOM后降级算作正常通过。
- 模型服务默认仅绑定127.0.0.1；若以后后端迁到VM，再评审网络访问、鉴权和网络时延，不能继续使用指向VM自身的127.0.0.1。

## 从现有代码核对出的适配点

1. **Embedding用途与索引。** 当前 `ModelGateway` 发送的请求只有 model/input，未区分查询和文档。Qwen查询应使用固定检索任务指令，文档按其文档编码路径；采用末token池化和L2归一化，写入/查询均固定同一修订。需显式传递 query/document 用途，在适配层实现并测试，不能对两种输入盲目加相同前缀。参考 [官方推理示例](https://github.com/QwenLM/Qwen3-Embedding)。
2. **模型替换。** 示例中的 BGE-M3 与当前检索模型/服务修订过滤需要同步演进；只改配置会出现已有向量不可用或错误混用。通过现有知识发布/索引版本生命周期构建Qwen向量、验证检索和引用，再切换；旧版本缓存失效且可回退。不重写已应用数据库迁移。
3. **DeepSeek模式。** 当前适配器没有思考模式配置，也没有保留 `reasoning_content`。官方当前文档说明思考模式默认开启，并对携带工具的历史消息有额外要求。建议临时基线显式关闭思考模式，先验证工具调用、JSON和多轮；若以后启用思考，另做服务专用适配，不把思考内容展示给顾客或写入普通日志。第三方托管的DeepSeek以实际服务能力为准。参考 [官方思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)、[工具调用](https://api-docs.deepseek.com/guides/tool_calls/)。
4. **结构化输出。** 当前 chat/sql均会请求JSON，而普通客服最终话术应可读、工具参数要严格。应按任务选择JSON或工具调用策略；取消/案例/SQL的JSON仍按本项目Schema验证。JSON合法不代表契约成立；空内容、截断、未知字段或工具参数不合规不得触发写操作。参考 [官方JSON说明](https://api-docs.deepseek.com/guides/json_mode/)。
5. **SQL校准。** 当前计划成本阈值未配置时生成SQL执行关闭。真实模型就绪不自动打开执行；先在隔离数据上校准阈值并跑越权/复杂查询反例。DeepSeek测得的是临时基线，不能当作03微调模型成绩。
6. **流式与费用。** 当前 `chat_stream` 聚合完成响应后返回，不能据此承诺逐token首段时延。真实接入补测首段、完整耗时、工具超时和断流；客服与SQL分别计费记录，供应商总用量合计。固定请求/输出token上限、重试上限及测试调用上限，较大评测先明确费用上限；不能因自动重试重复执行已确认业务动作。

## 可复现验证与后续切换

先做离线权重/依赖核对与单进程显存测试，再验证两模型常驻/队列/超时和中文检索。DeepSeek连接就绪后，先做小规模结构化输出、工具、多轮、SSE及SQL兼容测试，再运行已批准的RAG/SQL/多轮/Skill质量集、业务回归与完整负载。记录实际显存峰值、排队及P95、错误/降级、token用量、模型标识和修订、Schema/索引/测试集版本。不能用供应商支持声明代替本项目运行通过。

03交付时对 `sql` 配置切换地址/模型/协议及服务修订；主客服与Qwen检索无需连带更换。先兼容测试，再同一SQL留出集和业务回归；保留临时DeepSeek配置供受控回退，不让其静默兜底掩盖新模型失败。02/03共享契约仍待共同确认，不代兄弟项目签收。
