## 五、SFT → GRPO路线的必要控制点

### SFT

- 锁定Base权重、tokenizer、输入序列化、特殊token/EOS、输出格式及loss mask；不能照搬Instruct/思考模型模板，训练与API适配的模板保持一致并实际验证。
- 用相同数据版本与口径记录Base基线、SFT结果，后续再加入SFT+GRPO。临时deepseek-flash可作为另列的业务参考，但不能冒充同底座训练前基线。
- 全参/LoRA/QLoRA、精度、长度、批量、累积、学习率与训练量，按实际AutoDL资源和小试结果评审；不要现在凭“8B”保证某卡能跑。
- 先验证少量样本能学习、输出可解析且能产生部分正确候选，再扩大训练。loss下降、checkpoint文件存在都不等于业务能力提高。

### GRPO

- 从明确的SFT检查点继续，先离线验证reward和小规模rollout，再正式训练；不跳过这一步直接长跑。
- SQL语法正确或可执行只是一层信号。主要目标是受约束的业务语义/结果正确；同时处理输出契约、资源范围、澄清/拒绝、超时。权重和门槛待评审，不默认照搬数学题奖励。
- 安全、语义与格式分层；危险或越权候选不得因格式/长度分获得正向成功评价。拒绝/澄清也不能成为所有问题都拿分的捷径。
- 防止reward hacking：硬编码结果、恒空SQL、删过滤条件、错误关联、利用沙箱漏洞、忽略未知值、用无意义长输出骗分。隔离SQL执行权限和函数/资源白名单，限制单题耗时、行数和并发，失败归因不能一律罚模型。
- 记录group候选数、各奖励分量、正确率、组内奖励差异、全零/无差异组、输出长度/截断、KL（若启用）与训练/生成显存。奖励无区分度或异常升高时先诊断，不用更多GPU小时掩盖问题。
- 与SFT使用同一冻结评测协议，验证GRPO的增益及退化；不能只展示reward曲线上涨。未达标如实交付实验结论，保留SFT回退，不自动替换业务模型。
