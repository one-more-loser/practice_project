## Q-01-02 订单数量口径

**结论：orders.count与固定orders.summary一致；“下了多少单”需要澄清或明确题面。**

两者注册/实现口径是：本人+店铺+批次+代次范围，按 `created_at >= start_at AND created_at < end_at` 圈单，再限定：

```sql
trade_status IN ('paid','completed','cancelled_refunded','closed_refunded')
AND paid_minor > 0
```

未支付awaiting_payment和未支付取消cancelled_unpaid不计；已付后取消并退款、完成后全退仍计入已支付订单数，不因净额归零删除订单。不是按paid_at圈单，也不是退款事件数。

“本期创建总订单数，含未付/取消”可以对cs_order_self直接COUNT(*)，但它不是已注册orders.count；“有效订单数”还可能要求排除已付取消，不能偷换过滤。用户题面未说明时，询问是创建总数、已付数还是排除取消后的有效数。

时间参数缺省时，固定summary用[end−30天,end)，缺end则取传入now；SQL层却不会自动给裸SELECT加日期过滤（Q-01-04）。03调研建议“把orders.count改为含未付以与实现一致”方向错误：实现目前就是已付过滤。

**对03影响**：分别标`orders.created_count`（仅建议新语义名，不声称已注册）与注册orders.count；fixture须含跨月建单/付款、未付取消、已付全退、完成、部分退款，COUNT对照不能全用paid样本。

**最小方案**：先改自然语言题面/指标映射，不改现有指标行为。若产品决定增加创建总数，另审新指标及版本，不原地改变orders.count；用同一fixture比较两个计数。

## Q-01-03 支付、退款和净额

**结论：四注册指标按现状采用；本期到账退款有钱包替代面；退款率需明确口径并另行冻结，不能一概断言SQL无法表达。**

令C为Q-01-02建单窗内、4状态且paid_minor>0的订单集合：

| 注册键 | 公式 | 时间与范围 |
| --- | --- | --- |
| orders.count | COUNT(C) | 订单粒度，created_at半开窗 |
| orders.paid_minor | ΣC paid_minor | 原实付含运费，后续退款不冲减原paid |
| orders.refunded_minor | ΣC refunded_minor | 这些订单当前可见状态的成功累计退款，含窗口后发生的退款 |
| orders.net_paid_minor | ΣC(paid_minor−refunded_minor) | 同一订单集合；当前订单约束使结果≥0 |

空集合summary计数0、金额字符串"0"；注册键与响应字段order_count等是映射关系，不是“必须二选一”的冲突。裸SUM空集合为NULL，COALESCE才变0。网关只核metric_revision字符串，不验证候选SQL是否实现该指标公式；Executor本身不收metric_revision，03必须独立校验公式，不能把版本匹配当语义正确。

“某月创建订单的累计退款”可查询cs_order_self，按created_at选集合；`end_at`不是退款截止。`paid_at`也已在视图，明确“某月发生付款的订单原实付”可按paid_at过滤，属于非这四注册指标的显式SQL口径，不能因此说01所有SQL只支持created_at。

**纠正03调研的绝对结论**：`cs_wallet_entry_self`含kind、amount_minor、occurred_at；取消已付订单和正式售后成功退款均调用post_entry(kind='refund')。所以“某月成功退回本人钱包的金额”可用：

```sql
SELECT COALESCE(SUM(amount_minor),0) AS refund_minor
FROM cs_wallet_entry_self
WHERE kind='refund' AND occurred_at>=:start_at AND occurred_at<:end_at
```

本轮该SQL通过真实validator；写入来源是源码确认，未在PG核验历史数据对账。这个面没有order_id/SKU/business_ref、退款商品/运费拆分，不能代替“该月退款涉及哪些订单/SKU/退款申请状态”的专用事件面，也不能与建单cohort逐单关联。不能把所有退款问题标unsupported。

退款率先澄清：订单数比还是金额比？按建单cohort、付款cohort还是现金期？退款截止何时？部分退款算退款订单吗？分母为0返回null还是无行？小数精度如何？四指标未注册比率，但缺NULLIF不等于所有表达式被禁：

```sql
SELECT SUM(refunded_minor)/SUM(paid_minor) AS refund_amount_rate
FROM cs_order_self
WHERE created_at>=:start_at AND created_at<:end_at
  AND trade_status IN ('paid','completed','cancelled_refunded','closed_refunded')
  AND paid_minor>0
HAVING SUM(paid_minor)>0
```

该候选及带1.0避免整数除法的标量子查询订单比率均通过validator；PG结果、精度、空分母语义本轮未实测。上例空分母给无行，并不兑现“返回一行null”；不自动成为注册指标。跨事件订单退款率仍缺关联资源。03不能自行补业务公式或把比率/时区计算搬到模型服务后处理并宣称01支持。

**对03影响**：将建单累计、付款事件、钱包退款到账、退款率分成不同metric_scope；保存澄清槽位与后续明确问题。S05/S06原题不能直接标成建单cohort金标。01订单负净额fixture不合法，02现金期负净额不能移植过来。

**最小方案**：先修标签/题面；确需完整退款事件查询时另审安全事件视图（统一售后/取消来源、订单关联、成功时点、金额分拆及本人RLS），比率则另冻公式/精度/零分母与指标版本；优先利用现有合法表达，不为过题放宽校验器。

## Q-01-04 SQL与参数限制

**结论：按当前validator的实际行为适配，同时单独做语义检查；不能把“能过AST”当完整业务合同。**

| 项 | 当前实现 |
| --- | --- |
| 参数名 | start_at、end_at、order_id、sku_id、status；SQLExecutor要求参数键与AST占位符集合完全相等 |
| 参数值 | 时间必须为Python aware datetime，成对且0<窗口≤366天；JSON字符串需调用方先解析。其他参数未实现逐名类型/枚举/长度校验，不等于允许乱用 |
| 占位符 | 推荐:name；本轮%(name)s也接受并规范化；$1和?拒绝。值由调用方绑定，不拼SQL、不让模型提供身份 |
| 基本形状 | 单条Select；≤8192字节、≤512节点、深度≤18、全树≤3 JOIN、≤2 CTE；非递归CTE与标量/IN子查询可用；UNION/递归/写语句拒绝 |
| 资源/投影 | 六裸视图；禁止schema/catalog前缀；除COUNT(*)外禁星号。输出别名唯一、[a-z][a-z0-9_]{0,79}，禁phone/address/street/password/secret/token/owner/staff/cost_片段 |
| 函数/表达式 | COUNT/SUM/MIN/MAX/AVG/COALESCE、DATE_TRUNC（day/week/month）、算术/比较/布尔/IN/BETWEEN/IS NULL；AST白名单最终决定，不存在任意函数自由调用 |
| 不支持的有意义写法 | CASE、CAST、NULLIF、ROUND、LIKE、窗口函数、FILTER、AT TIME ZONE、INTERVAL等当前拒绝；具体业务请求可能有别的合法写法，不等于请求本身一定unsupported |
| JOIN | ON单一Column=Column，两侧同名order_id/sku_id/shipment_id；不支持USING/复合条件/无ON。≤3 JOIN并不等于“最多三张表” |
| 聚合 | 单scope多来源时直接SUM/AVG拒ambiguous_grain；不是所有join后聚合都拒。COUNT join仍可重复计单，须金标检测fan-out |
| 字面量 | 字符串仅20个全局白名单；日期/ID/商品名字符串不能硬写。数值字面量≤1e9，合法负号由Neg节点表达；这个数值上限不等于数据库金额上限 |
| 行数/排序 | 缺LIMIT变20；字面量大于50被截到50，小于1拒绝；OFFSET整数字面量0..10000。可ORDER BY/HAVING/DISTINCT；有限结果要有稳定tie-breaker。返回不含has_more/truncated |
| 资源 | 连接3s；只读事务、UTC、search_path=csq,pg_catalog；statement_timeout 2000ms、lock_timeout 500ms；pool2+overflow2；EXPLAIN非ANALYZE，总成本不得超配置预算(0,100000]；fetchmany51，超过50拒 |

query_plan_cost_limit源码默认None，未设或无效时503 query_unavailable；本轮没有读取部署有效值，03沙箱必须另行校准，不能照搬历史测试预算为生产批准值。

合法候选（本轮已过validator，PG未实跑）：

```sql
-- 时间窗内已付订单的SKU商品实付，避免join后SUM
SELECT sku_id,SUM(paid_goods_minor) AS paid_goods_minor
FROM cs_order_item_self
WHERE order_id IN (
  SELECT order_id FROM cs_order_self
  WHERE created_at>=:start_at AND created_at<:end_at
    AND trade_status IN ('paid','completed','cancelled_refunded','closed_refunded')
    AND paid_minor>0
)
GROUP BY sku_id ORDER BY sku_id LIMIT 50
```

先按订单聚合行表的CTE、再JOIN订单进行明细投影也接受；见已有SQL安全测试。`LEFT JOIN cs_shipment_self ... ON order_id`及GROUP BY时间表达式也接受，调研“不支持非别名GROUP BY”的猜测不成立。

## Q-01-05 时间与时区

**结论：上海自然日/周的单窗过滤可用；当前正式参数面不支持上海分桶，不要套UTC桶。**

aware时间比较的是瞬时。2026-11-01上海自然日应绑定 `[2026-11-01T00:00+08:00,2026-11-02T00:00+08:00)`，即UTC `[10-31 16:00,11-01 16:00)`。2026-11月末用12-01 00:00+08作为不包含的end，不能把“到11月30日”机械绑定为11-30 00:00而漏整天。date_range并不强制end≤now，未来窗口也可过结构校验；03应冻结参考时钟，例如以12-10评测11月题，不能依赖执行机器当天日期。

Executor会话固定UTC；DATE_TRUNC('day'/'week'/'month',timestamptz)依此分桶，周以周一为界。例：11-01 00:30+08=10-31 16:30Z，上海日是11-01，UTC日桶为10-31；11-02周一00:30+08=11-01周日16:30Z，上海周起点11-02，UTC周起点仍10-26。此处是PG语义静态推断及Python时区换算，未做本轮PG执行。

本轮validator接受UTC day/week以及GROUP BY表达式；拒绝字面量Asia/Shanghai的三参数DATE_TRUNC、AT TIME ZONE和INTERVAL平移。借:status传时区虽能过AST，但违背status业务用途且客服工具无法绑定它，03不得训练此写法作为支持证明。

**对03影响**：S03单日COUNT可用上海起止参数，不必分桶；S04“按上海每周分组”当前应明确暂不支持或另审。题面写UTC周才可用现成week桶；一周总数可用上海周一到下周一的单窗过滤。不要让模型服务隐式后处理结果冒充SQL能力。

**最小方案**：另审受控timezone参数/固定允许Asia/Shanghai的DATE_TRUNC形式，或业务视图增加明确上海桶列，更新Schema/校验与调用方；验证日/月/周边界、半开窗、timestamp类型和调用方解析。不能由03自行改变01连接时区。

## Q-01-06 数据版本与可重放

## Q-01-08 金额、关联与跨项目映射

**结论：01金额定义按现状采用；已有01→02映射，不能沿用“全部待对齐”，但适配范围有明确限制。**

| 量 | 定义/合法边界 |
| --- | --- |
| goods_minor | 订单商品原额，>0；订单行=unit_price_minor×ordered_qty |
| discount_minor | 商品优惠，≥0；行allocated_minor=goods_minor−discount_minor |
| freight_minor | 订单运费，≥0，不在SQL订单行金额中分摊 |
| payable_minor | goods−discount+freight |
| paid_minor | 原实付；支付流程成功时=payable，未付为0；DB CHECK要求0≤paid≤payable |
| refunded_minor | refunded_goods+refunded_freight，0≤refunded≤paid；成功累计，非待审批申请额 |
| 行paid_goods_minor | 未付0，成功支付时=allocated；不含运费 |
| 行remaining_qty | ordered−refunded−reserved_refund_qty；是退款数量余量上限，非未履约件数，也不单独证明订单满足退款资格 |
| 行remaining_goods_minor | paid_goods−refunded_goods−reserved_refund_minor，非净支付（含正在占用的退款额度扣减） |
