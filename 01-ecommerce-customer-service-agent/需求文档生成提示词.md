**已确认的项目定位**

我们建设模拟电商店铺中的顾客端客服 Agent。顾客在商城使用嵌入式客服，咨询商品和政策，查询本人订单、物流与售后，必要时澄清、建立工单或转人工。

同一总目录另有两个独立项目：02-ecommerce-operations-agent 负责经营分析与促销筹备；03-ecommerce-text2sql-finetuning 负责 SQL 模型的数据、训练与评测。本项目需要规划接口边界，不代替它们实施。

RAG 是客服内部的知识工具；SQL 模型是可替换的查询生成组件，不把它们各自计为一个新的业务 Agent 项目。电商行业已确认，不再推荐其他行业。

**需求需要覆盖的业务**

1. 模拟商城载体：提出支撑客服演示所需的最小商品、登录、订单页面及模拟交易能力范围；购物车、模拟支付等按 P0/P1/后续列清，不扩大为接入真实资金的商业支付平台。
2. 商品与政策咨询：商品说明、运费、优惠、退换货、保修等知识的来源、版本、有效期、检索与引用；资料不足、矛盾、过期和无关时的处理。
3. 业务事实查询：商品/SKU、库存、本人订单、物流、售后；多轮澄清、指代、查询条件变更和多意图的处理；没有真实数据时的样本需求与模拟边界。
4. 受控 Text-to-SQL：检索相关 Schema 和指标定义，生成并校验只读查询，限制数据范围、返回数量和执行成本。身份从可信登录态取得，顾客只能访问本人授权数据，权限不依赖 Prompt 或模型自行补 WHERE。
5. 业务动作与人工协同：工单创建、查询、分派、投诉升级与人工接管的基线范围；退款申请、取消订单、改址等动作列出优先级、业务前置条件和确认机制，通过业务接口执行，不让模型生成任意写 SQL。
6. 会话与任务：会话归属、消息顺序、流式反馈、工具执行状态、失败、超时、重试、重复提交、人工接管与恢复、历史查询；说明关键状态和可观察行为。
7. 运营反馈：向第二个项目提供可用的咨询热点、知识缺口、投诉主题和工单统计，明确字段类别、权限、数据归属、时间范围和对接状态，不在本项目实现促销决策。
8. SQL 模型对接：向第三个项目提出 Schema、指标、问题类别、目标输出、错误语义和版本兼容需求；规划训练前使用基线模型的方式，不将训练完成作为本项目需求文档的前置条件。

**分析方式与文档质量**

- 先用一段话复述目标和范围，再开展分析；已有决定不重复询问。
- 若缺失信息会改变业务范围、权限或验收，集中提出最多 3 个关键问题，同时推进不依赖答案的内容。其余采用有理由的默认假设，并记录影响；不要为界面配色或框架偏好阻塞需求。
- 原 MD 是需求来源，不代表所有条目都要整套实现；列明“采用的需求、裁剪范围、新增的连接需求”。不要把部分能力组合称为完成整个 2.6 或 2.9。
- 本阶段不锁定未经评估的技术栈，不生成业务代码，不克隆安装项目、不启动服务。复用方案只做适配与差距分析，不用现成仓库的功能列表替代业务需求。
- 功能需求采用 FR-CS-xxx，业务规则采用 BR-CS-xxx，非功能需求采用 NFR-CS-xxx，验收项采用 AC-CS-xxx。用户故事可以使用 US-CS-xxx。编号需唯一并相互关联。
- 每条功能需求应说明角色、触发、前置条件、输入、正常流程、异常/拒绝分支、状态/输出、权限和验收条件。可复用通用规则，避免重复罗列。
- RAG、SQL 与业务接口要区分数据来源；模型不能把未查询到的价格、状态、库存或政策说成已确认事实。
- 提出响应时延、并发、可用性、检索/引用、SQL 结果正确性等可测指标，写明测量条件。建议数值标注“待评审”，不把假设或开源作者成绩写成本项目既有结果。
- 数据部分明确订单与订单明细粒度、商品/SKU、顾客身份、金额与退款口径、时间与时区、知识版本、数据脱敏和来源。截图中的约 38 万订单与 9.8 万用户未经过 CSV 核验；它们也不是 SQL 训练标签。
- 共享数据、接口和事件仅提出可评审契约草案与归属建议，不擅自规定兄弟项目已实现什么，也不修改兄弟项目。
- 公司流程按本项目规模落实为可评审、可追溯、可测试的成果，避免空模板和只写口号。
