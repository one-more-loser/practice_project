## 2. 业务目标与边界

为店铺管理者在 618、双十一等活动前后提供可追溯的经营判断和方案比较：

`经营目标/问题 → 获准经营数据与市场证据 → 工具查询与确定性测算 → 候选方案比较 → 人工决策 → 监控与复盘`

需求应覆盖并划分优先级：

| 能力 | 要解决的问题 | 输出要求 |
| --- | --- | --- |
| 经营问数与诊断 | 哪些商品、时段或渠道表现异常，活动依据是什么 | 带口径、时间窗、数据来源的指标与拆解；区分关联解释与根因 |
| 市场与竞品证据 | 可比商品的价格和活动有什么变化 | 有来源、时间、地区、规格、价格组成与有效期的证据；缺证据标未知 |
| 促销方案比较 | 折扣、优惠券等规则在预算与利润约束下如何取舍 | 候选、计算明细、排名依据、被淘汰原因与适用条件 |
| 备货与履约风险 | 各销量情景下会缺多少货、何时补、履约是否承受得住 | 当前可用库存/在途与到货时点、资源缺口、风险阈值和建议 |
| 人员产能 | 客服、仓储等环节需要多少可用工时或班次容量 | 基于明确生产率和需求假设的容量缺口，不凭销量编造个人排班 |
| 监控与复盘 | 活动偏离了什么，结果与计划为何不同 | 计划/实际比较、告警规则、证据和调整建议；无实验依据不承诺因果增量 |

建议首个可验收闭环为：选定一批 SKU 和活动目标，读取或导入一份来源明确的经营快照，计算若干促销候选的预算/利润/库存约束，比较并保存方案与假设。竞品可先用人工整理的证据，产能可先按岗位容量测算，监控可先用历史回放或数据导入。这是供评审的实施顺序，不是已批准删减功能；完整目标与后续迭代保留在 PRD。

- 01 负责商城交易、履约、客服与工单；02 不重建商城、支付、余额和售后系统。
- 03 负责 Text-to-SQL 数据、训练、推理与独立评测；02 提出经营查询的逻辑 Schema、指标和任务需求，不在这里开展微调。
- 初始方案以分析和建议为主。发布活动、改价、采购、改库存等执行能力若要纳入，单列业务权限和验收，不因方案生成就自动执行。对外发送消息须有用户明确指示。
- 店铺/角色范围由后端授权；不靠提示词或模型生成的 WHERE 限权。SQL 生成候选与受控只读执行分开，写操作使用获批业务 API。

## 3. 先确定数据与口径，减少计算返工

先列“业务问题 → 所需字段/粒度 → 来源及提供方 → 质量/更新频率 → 缺口处理”，再定表和工具。用户曾提供的数据介绍截图不是已接入数据，也不是 SQL 标注集；先核对本次实际收到的文件和样本。01 已有模拟业务库也不代表 02 已取得全店经营数据。缺数时用显式合成样本推进规则验证，保留来源标记，不宣称真实经营效果。

- 明确订单/明细/SKU 粒度、时区和半开时间窗、支付/取消/退款处理、金额单位及舍入、折扣叠加、指标分母、去重及成本归属。不要多表关联后重复累计订单金额。
- 金额、利润、补贴、库存、预算、工时及约束筛选由可测试代码计算；模型负责理解问题、选工具和解释。毛利、贡献利润、促销 ROI 的口径分开定义，缺少成本/费用或必要对照时不输出伪精确指标。
- 成本、库存时点、补货提前期、价格弹性、转化率和岗位生产率缺失时，给出缺口或标明情景假设；缺失/被抑制值不当作 0。“销量增长 10% 时的结果”不等于“活动会增长 10%”。
- 每个方案记录数据快照、指标口径、假设、计算版本和方案版本，结果能追溯重算。数据或关键规则变化后怎样重算、失效或重新确认，在需求中定义。

## 4. 先对齐当前这条链路的契约

在依赖进入开发前明确生产方、消费方、权威来源、店铺/SKU 标识映射、权限、粒度/单位、更新时点、版本、错误和正常/空/过期/重复样本。先对齐本批用到的接口，不一次设计整个企业平台。

01→02 的客服聚合与全店经营事实是两类输入。投诉/咨询主题不能替代销售额、退款率或库存事实。01 当前契约仍是生产方提案，需 02 签收；早期草案路径和示例指标不能直接写成已可用 API。其当前聚合按已结束的周窗提供，不能假定支持活动当日实时告警；若需更细粒度，提出契约差异和备选数据源，不自行修改 01。

消费快照保留：`event_id` 去重、`snapshot_id/revision` 替换而非累加、多主题非可加总、小样本抑制/迟到/缺失标记。不能为补统计索取客服个人明细。

02→03 的经营查询 Schema 与 01 的“顾客本人”查询范围不同，应单独声明。03 未就绪时，可用获准基线服务或带标记的契约替身推进；真实切换再做协议与业务回归，不把替身当真实联调，也不以微调评分替代经营查询正确性。

## 5. 复用要降低依赖，验证要定位风险

保留 01 的可复用模块和开发习惯，避免整仓复制。Vue/TypeScript、FastAPI、PostgreSQL、LangGraph 是候选，不因 01 使用就全部引入；有确定性规则的步骤用业务服务，Agent 图只承载必要的工具路由、状态与决策。没有用途就不建向量库、消息中间件或复杂多 Agent 层。

真正接入模型时再核对本会话获准的型号、配置入口及预算。01 的 deepseek-flash 配置和既有调用授权不自动成为 02 的固定要求。已有可用服务优先评估复用，按能力隔离 chat/sql 等适配；用实际 JSON Schema/Pydantic 校验输出，不凭可解析 JSON 就执行，也不补造 SQL、身份或金额来修复错误。

普通自动化测试使用可控替身，真实模型检查单设入口并限制请求、token、超时和重试。先验证小样本协议与关键业务，接口/规则稳定后做质量与负载验证；共享供应商额度或硬件要合并考虑。只有确需检索时才核对共享模型文件、编码用途和资源容量，不先下载模型或调优临时服务。

每次改动跑相关检查；跨模块变更、阶段出口或新风险出现时扩大回归。业务优先检查金额/舍入、折扣规则、预算/库存边界、缺数处理、店铺越权、重复消费、数据过期和方案失效。保留首次失败与最小复现，不无限重跑到偶然通过。

静态检查、替身、真实数据库/HTTP、真实模型和跨项目联调分别登记，结果绑定当次源码与数据/服务版本。前端类型检查不代替构建与实际页面；工具成功不代替最终结论相关、数字一致、依据清楚。完整质量/稳定性目标按 02 需求确定，不能照搬 01 的测试数、并发数与持续时长，也不能把关键正确性留到最后。

数据库和服务操作到对应阶段再处理：应用/测试库隔离，重置前验证目标；共享写环境串行或分别隔离；只管理归属明确的进程、端口和卷；不复制 01 密钥、写凭据、数据库重置或部署命令。涉及部署时，验收增加查询耗时、响应时延、调用成本、并发容量及资源开销，数值由场景和实测确定。
