# 02 执行桥实际契约 XOPS-ACTIVITY-v0.1

本文件对应02当前桥实现。只实现并测试02；01接口是对方待实现/签收的契约，未调用真实01。JSON Schema见 `contracts/activity-v0.1.json`。金额为非负整数分字符串，数量/修订为JSON整数；时间带时区；CNY；未知执行结果不能推断无效果。

## 1. HTTP与身份

成功统一包装为 `{"data": <下述对象>}`，错误使用非2xx。内部API须 `Authorization: Bearer <部署配置的专用服务密钥>`，且store_id必须在02配置 `service_stores` 白名单内。部署不配置密钥/店铺时失败关闭。01身份Cookie只能发往02服务器配置的01地址，不随客户端URL变更，不跟随重定向；预检转发cs_session与当前可信Principal绑定的X-CSRF-Token，Origin使用服务器配置。HTTP总客户端超时配置3秒，无自动重试，调用期间不持02事务锁。

02的真实预检 `Bridge.preview` 固定调用：

```http
POST /api/v1/shop/activity-previews
Cookie: cs_session=<当前真实会话>
X-CSRF-Token: <当前会话令牌>
Origin: <部署配置的商城Origin>
Content-Type: application/json
```

请求为 `{contract_version,store_id,plan_id,plan_version,manifest_digest,manifest}`。服务器从受控方案/快照构造manifest，禁止从浏览器接受actor、价格版本或最终执行金额。01成功响应data为：

```json
{
  "contract_version":"XOPS-ACTIVITY-v0.1","store_id":"store_A",
  "plan_id":"plan_A","plan_version":1,"manifest_digest":"<64位SHA256>",
  "preview_ref":"preview_A","status":"passed",
  "expires_at":"2026-11-10T12:05:00+08:00"
}
```

上述绑定字段全部与请求一致；expires_at须晚于02可信时钟且最多5分钟。01须在本地检查当前权限、价格/库存版本、可售、同SKU活动冲突及预期执行能力。02不把本地经营通过或快照自报能力当作01预检。响应额外字段不回传前端。真实网络结果加 `evidence_kind=integration`；显式注入测试transport加 `contract_stub`，后者不能用于真实确认/授权。

## 2. 固定Manifest与摘要

示例（JSON内占位摘要须替换，不能复制占位值执行）：

```json
{
  "contract_version":"XOPS-ACTIVITY-v0.1","store_id":"store_A","plan_id":"plan_A",
  "plan_version":1,"rule":"direct","currency":"CNY",
  "start_at":"2026-11-11T00:00:00+08:00","end_at":"2026-11-12T00:00:00+08:00",
  "scenario_policy":"base","budget_cap_minor":"100000","fixed_fee_minor":"10000",
  "variable_budget_cap_minor":"90000",
  "lines":[{"sku_id":"A","base_price_minor":"10000","activity_price_minor":"9200",
            "quantity_cap":100,"price_version":1}],
  "source_snapshot_id":"snapshot_gold","source_snapshot_revision":1,
  "source_kind":"business_import"
}
```

`manifest_digest = SHA256(UTF8(json.dumps(manifest, ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False)))`，小写hex。行按sku_id升序；行内数值只采用当前不可变方案与对应受控快照。quantity_cap取选中low/base/high情景，all取high；零数量不签执行授权。base_price_minor/price_version只取快照SKU，activity_price_minor取直降方案；预算可变上限=总预算−固定费预算占用。固定费占用不是现金扣款。

01可将完整manifest原样保存/传回02，避免不同语言Unicode或时间字符串重写影响摘要。需要01独立生成摘要时采用相同序列化规则，禁止将字符串金额改成数字或改写时间。首版只支持direct；券与baseline不能签发。

## 3. 01读取方案与取得一次授权

1. `GET /api/ops/v1/internal/plan-revisions/{plan_id}?store_id=store_A`。data包含contract_version/store_id/plan_id/plan_version/status/manifest/manifest_digest/approval_ref。只返回执行投影，不包含成本与资源私有细节。01必须检查status为confirmed，并从02读取，不信任前端的投影副本。
2. 用户明确发布后，01在本地创建唯一slot `(store_id,plan_id,plan_version,approval_ref)`，服务端生成intent_id；slot创建/查找幂等，即使浏览器换键也不能再建一个执行意图。
3. 01调用 `POST /api/ops/v1/internal/execution-grants`，JSON示例：

```json
{
  "store_id":"store_A","plan_id":"plan_A","approval_ref":"approval_A",
  "intent_id":"intent_A","manifest_digest":"<64位SHA256>","actor_ref":"manager",
  "auth_version":1,"capability_revision":2,"preview_ref":"preview_A"
}
```

app移除store_id/plan_id交Bridge.grant。其余字段精确匹配Schema，未知字段拒绝。actor/auth_version/capability_revision由01当前可信会话与发布权限校验产生，并与审批记录绑定，浏览器自报不能作为证据。02锁同店铺范围，重新读取current plan revision、受控快照、数据库测算与审批，重新运行经营/资源/任务检查；新快照修订、过期预检、demo/sandbox/contract_stub审批均拒绝。

授权data包含contract_version、grant_ref、approval_ref、intent_id、store_id、plan_id、plan_version、manifest_digest、manifest、actor_ref、auth_version、capability_revision、preview_ref、issued_at、expires_at。期限60秒，保存原始grant及请求摘要。一个审批只绑定一个intent；同审批/同完整请求返回原grant，过期/终态也不续签；换intent或身份断言拒绝。intent_id亦全局唯一。旧审批不能结束后再发一次活动。

本版本统一字段名为 **intent_id**，不接收execution_intent_id别名。01若内部使用execution_intent_id，仅在API适配层映射一次。

01取得grant后必须在本地发布短事务重新锁主体/能力、slot、SKU/库存/额度；验证原grant绑定、有效期、实时权限/能力修订、最新价格版本与冲突。01事务内不能调用02。仅在到期前进入并在slot临界区接受授权的事务可完成，01是最终执行权威。02签grant时已冻结批准的经营假设；新导入数据不能单方解冻在途意图。

## 4. 持久终态回执与活动投影

01 `POST /api/ops/v1/internal/execution-receipts`，完整JSON：

```json
{
  "contract_version":"XOPS-ACTIVITY-v0.1","event_id":"event_A","store_id":"store_A",
  "intent_id":"intent_A","approval_ref":"approval_A","manifest_digest":"<64位SHA256>",
  "status":"committed","terminal_revision":1,
  "activity_id":"activity_A","activity_revision":1,"phase":"scheduled"
}
```

status只接受committed与closed_no_effect。committed必须有activity_id、正整数activity_revision及phase（scheduled/active/paused/ended）；closed_no_effect的activity_id/activity_revision/phase必须为null，并必须携带正整数terminal_revision。后者表示01已持久关闭slot、所有迟到发布都将拒绝。event_id重送同内容幂等，不同内容拒绝；必须绑定本店grant的intent/approval/manifest摘要。slot终态不能反转，terminal_revision保持不变。相同committed终态可用新event_id和更高activity_revision推送phase变化；旧活动修订不覆盖新投影，同修订不同phase拒绝，ended不可用高修订重开。活动不能绑定其他店铺或方案。

暂停/恢复/结束由01管理API执行，再发送同一committed slot终态的phase修订回执。02签grant同事务把方案设publishing；可信回执把方案设最新phase或closed_no_effect。未知及本地过期均不解冻，同审批始终不能重开。

## 5. 未知结果与终态屏障

02后台/管理端对账入口为 `POST /api/ops/v1/internal/executions/{intent_id}/reconcile`，body为 `{"store_id":"store_A","finalize":false}`。01也可直接推送上一节回执。

02读取原grant后在事务外发出：

- 普通查询：`GET /api/v1/internal/stores/{store_id}/execution-intents/{intent_id}`。
- 授权已过期才允许：`POST /api/v1/internal/stores/{store_id}/execution-intents/{intent_id}/finalize-expired`。

均带专用Bearer。成功终态的data必须与上一节完整回执相同。01尚未判定时可返回data `{"status":"unknown"}`。超时、404、坏契约、查不到slot、服务未配置、仍在途，一律返回02 `status=result_unknown`，保留冻结，不制造closed_no_effect。

01 finalize-expired须锁同slot，取得锁后检查可信时钟并读取最新状态；在途事务等待超时则unknown；committed返回原活动；否则持久写closed_no_effect和terminal_revision，在同一锁屏障上封闭所有迟到发布。02不通过本地过期定时器解冻。

### 撤销在途执行（cancel-request）

02桥方法 `cancel(store_id,intent_id,actor_context)` 只接收上层已鉴权服务构造的actor_context，精确字段为actor_ref/auth_version/capability_revision/reason（原因非空、最多1000字符）。读取本店受控grant后，在02事务外调用01：

```http
POST /api/v1/internal/stores/{store_id}/execution-intents/{intent_id}/cancel-request
Authorization: Bearer <配置的专用服务密钥>
Content-Type: application/json
```

JSON为 `{actor_ref,auth_version,capability_revision,reason,grant_ref}`；grant_ref取02数据库记录，不能由浏览器或actor_context覆盖。01须重新检查当前主体/能力断言并锁同一slot屏障：未提交则持久封闭为closed_no_effect并返回完整终态回执；已提交返回committed及活动事实，不自动暂停。02按本文回执契约校验并落库；已有可信终态时直接返回该事实。未配置、HTTP超时、404、坏契约或其他意图响应均返回result_unknown，保留冻结，不报告cancelled。此路径不以授权尚未到期为理由阻止撤销，但必须通过01的slot屏障判定最终效果。

## 6. 活动实际聚合修订

01 `POST /api/ops/v1/internal/activity-actuals`，示例：

```json
{
  "contract_version":"XOPS-ACTIVITY-v0.1","store_id":"store_A","snapshot_id":"actual_A",
  "activity_id":"activity_A","revision":2,"source_kind":"business_import",
  "watermark":"2026-11-11T12:00:00+08:00",
  "window_start":"2026-11-11T00:00:00+08:00","window_end":"2026-11-12T00:00:00+08:00",
  "bucket":"activity_cumulative","payment_minor":"100",
  "refund_minor":"20","consumed_discount_minor":"5","reserved_discount_minor":"0","paid_units":1
}
```

必须已有本店可信活动回执。window_start/window_end必须等于原manifest活动窗；bucket固定activity_cumulative，表示按活动归属累计到watermark的实际，后付/后退沿原活动累计，活动窗口用于关联原计划。snapshot_id代表同一活动的累计聚合序列；revision递增表示整批替换，不能把各revision相加。相同revision/相同内容幂等，内容冲突拒绝；旧revision返回当前最新批次，不覆盖；新revision watermark不得倒退或来自未来。snapshot_id不能换绑活动。watermark是01可见数据时点；payment与refund分别表示原始累计支付/成功退款，paid_units为支付销量，不自动减退货。金额均非负；净值由02按口径计算。

01负责订单、支付、退款、数量/让利预占和核销账本。付款后退款不恢复营销额度的保守规则在01执行，02不会从退款金额回补额度。source_kind沿事实来源保存，synthetic或derived不能被02洗成真实业务。

## 7. 已验证与未验证

补充约束：同一(store,activity_id,bucket,原活动窗)固定snapshot_id，不能换ID从revision=1重开；监控还按watermark防御性取最新。活动开始前watermark的非零成交/额度/销量拒收。时间比较按等价瞬间，保留原manifest时间字符串参与摘要。

管理端补充API：`POST /api/ops/v1/plans/{id}/cancel-approval`，`{expected_version,reason}`（理由≤1000字），需当前plan.confirm/cost.read、Origin/CSRF和幂等键。未签grant时与grant共用店铺锁，直接cancelled并阻止迟到grant；已签grant写cancel_pending及不可变撤销请求，再在事务外调用01 cancel-request，unknown不宣布撤销成功。已知committed保留真实phase，需在01暂停/结束。

`POST /api/ops/v1/plans/{id}/reconcile-execution`，`{expected_version}`，同样在线权限与CSRF；普通未决查询01，授权到期时请求slot终态封闭；撤销待核对时重试原取消意图，当前身份版本重新校验。返回当前Plan，若仍publishing/cancel_pending即未证实终态。内部服务对账入口仍保留，供双方恢复流程使用。

验证为02 SQLite服务类与HTTP MockTransport行为测试，包括摘要/身份/修订绑定、审批唯一、过期不续签、无效果持久终态、冲突回执、HTTP超时/404保留未知、实际revision替换。没有真实01 HTTP、PostgreSQL并发、商城购买、生产部署、模型调用或性能基线证据。
