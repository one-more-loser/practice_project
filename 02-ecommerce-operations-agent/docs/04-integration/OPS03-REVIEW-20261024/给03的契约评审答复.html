Q-02-05 as_of、快照、revision、watermark 与重放

当前事实与依据（S）：domain.py:251–261 为 visible=min(传入as_of, snapshot.as_of)，事件 <= visible。service.py:172–187 传的是业务 clock。HTTP dashboard（app.py:167–171）仅有 snapshot_id/start_at/end_at/sku_id/channel；没有 as_of/revision；额外加到URL不构成有效选择器，不得因请求成功就认为已生效。指定 ID 取最高修订，不指定则各 ID 头中按归档 created_at 排序（service.py:66–81），不是最新 watermark。同三元组内容冲突拒绝（:99–106）；旧修订归档/父链导出在 :596–609。测试：test_domain.py:129/141/161；test_api.py:141/218。

结论：需要修订；不同意 snapshot_id 或 as_of 二选一足以重放。 训练/评测至少固定 profile、店铺隔离标记（仅沙箱/业务内部）、snapshot_id、revision、归档 digest、evaluation_as_of、查询窗、筛选、Schema/指标/校验器版本。旧标签不随新 revision 改写；迟到事件用新修订、新结果标签。

最小方案（I）：02 增加精确修订读取＋受控 as_of，校验归档 digest，返回 snapshot 引用、watermark=源 as_of、requested_as_of、effective visible_at、source_kind。缺省取头仅用于现有交互，不用于金标；as_of 不能代替数据身份。事件恰在 visible 纳入，恰在 end 排除。

历史重放限制：当前快照没有逐事件“何时被系统获知”的时间，只有事件发生时间与固定归档版本。新快照按旧 as_of 截断不等于重建当时已知事实；只能声称“固定归档版本上的事件时间重算”。如需双时间/当时状态重建，须另增 ingestion/有效期来源与版本。活动 actual 的 watermark/revision 与经营 snapshot 分开，不能混用。

训练影响/验证：03 fixture 必须包含不可变数据摘要，不能只绑定 schema_digest；Base/SFT/GRPO 使用同版沙箱和同组截止。补精确 revision、未来截止截断、旧修订、新到旧发生事件、同 ID 内容冲突及归档缺失反例。当前函数可做离线 oracle，不代表 HTTP 已支持这些请求。

Q-02-06 支付、退款、批次退款率与净额

当前事实与依据（S）：domain.py:266–295：支付按 paid_at 处于 [start,end) 且不晚于 visible；成功退款按 occurred_at 不晚于 visible，现金退款另要求在窗内，cohort 退款只要求原订单在支付 cohort，允许窗后退款。service.py:175–193 分别判定 SKU 的 cash_unknown 与 cohort_unknown。test_domain.py:98/150/161、test_repair_refund_history.py:67/89/107。

结论：可按现状采用；澄清策略需要新增。 同意显式指标族，不同意改字段名后当无缝兼容。“本期退款”默认解释现金期；“本期净实付”是本期支付减本期退款；“退款率”须澄清按支付批次的订单率还是金额率。当前没有现金退款/本期支付这一注册比率，不由模型自行发明。销售额/收入/利润混用也要澄清。缺时间窗的新模型交互建议澄清，保留旧 dashboard 的交互默认而非立即改动。

影响与最小验证（I/R）：03 样本不得把 01 的 created_at 圈单＋订单累计退款当 02 标签。四订单示例在本轮合成 fixture 中重算：11 月支付 60000、现金退款 10000、净额 50000，截止 12/10 的 cohort 订单率 0.666667、金额率 0.500000；这只验证 02，不替 01 验证其对照数字。不同 profile 可共用问法但必须带各自 Schema/指标/数据修订，不能以改表名合并标签。SQL 对照必须先分别聚合支付与退款，再组合，避免订单行×退款事件扇出。

Q-02-07 维度、粒度、时间桶与可加性

当前事实与依据（S）：service.py:145–173 支持单 SKU/channel 筛选，按原生行额投影订单支付；domain.py:276–307 的 channels 是 strip 后空→unknown 的完整支付分组。service.py:203–227 是上海自然日稀疏 history：只有支付、成功退款（含零额）或未知退款事件建桶，没有补齐日历。test_joint_operations.py:91；test_repair_refund_history.py:51/127/136。

结论：部分可采用，分组能力需准确收窄。 店铺只由服务端身份绑定；现有 channels 分组和单 SKU 筛选可用。没有每 SKU 一次 GROUP BY 返回所有 SKU 的 API，也没有周/月桶接口；逐个 SKU 调用不是已实现的批量分组。库存仅快照单时点，无仓/历史库存/访客/转化率。

可加性建议（I）：同一快照修订、窗、visible、SKU 条件，且渠道分组互斥、覆盖完整时，渠道 payment_minor 与 paid_order_count 可加总为总量。跨 SKU 的件数/原生行金额可在互斥完整分区下相加，但订单数因同单多 SKU 不可相加；均价、比例一律重新聚合分子/分母，不平均/相加。时间日桶的现金金额可按同窗可见事件求和；未知退款桶不能 COALESCE 成 0 再当已知总额。

影响与最小实现：03 训练“按每个 SKU/周/月/仓”前等待 02 分组/时区/行数契约；可先准备候选反例。02 后续增加批准的 group_by/bucket，仅依单时点库存不得推历史库存；03 分组 SQL 固定 Asia/Shanghai，不能照搬 01 UTC 会话。fixture 覆盖上海零点/UTC 等价、退款独占日、同单两 SKU、unknown 渠道与稀疏空日。

Q-02-11 响应类型、错误码与版本兼容

当前事实与依据（S）：现有 HTTP 成功 {data: ...}；失败 {error:{code,message},request_id} 与状态码（app.py:60–105）。assistant 返回 answer/mode/evidence/missing，局部分支有 status=clarify；不是 SQL-MODEL envelope。当前版本失败关闭存在于身份/快照/执行契约，并未实现 SQL 的 schema_digest 校验。

结论：建议接受 03 PRD 的统一 SQL-MODEL-v0.1 骨架＋显式 operations 扩展，不接受第二套近似字段同时使用。 四类互斥 query/clarify/unsupported/error；v1 非流式。使用 profile、parameter_names、clarify.slots、unsupported.reason_code、error.code、service.revision；不与评审包的 consumer_profile、parameters 描述数组、service_revision、顶层 reason_code 混写。

新协议与错误建议（I）：query 必有 sql 与参数名，其他三类不允许 SQL；版本/digest 不符→error/schema_mismatch 或 metric_mismatch；缺语义条件→clarify；写请求/未开放资源/不可用指标/成本能力→unsupported（capability_unavailable 不暴露敏感细节）；模型内部失败→error/model_unavailable。02 执行端另区分 unauthenticated(401)、forbidden(403)、不可访问资源(404，避免越店枚举)、invalid_parameters/window/filter(422)、revision_conflict(409)、query_limit_exceeded(422)、query_busy(429)、query_timeout/query_unavailable(503)。此为新层映射，不能假称是当前 HTTP 全部已有错误码。

影响/验证：见 request-response-examples.json。所有新信封均标 proposed_unimplemented，不能直接调用当前 dashboard；当前 API 样例单独标记。03 训练用单一 serializer、解析器和字段互斥校验；Base/SFT/GRPO 奖励同版，不能靠 JSON 合法掩盖 SQL/业务错误。业务执行拒绝不能被模型 unsupported 成功率掩盖。

Q-02-12 金额、比率、舍入、NULL、0 与空结果

当前事实与依据（S）：domain.py:20–21、60–68、118–121、299–307：输入金额非负整数分字符串且每项≤BIGINT，聚合用80位 Decimal 上下文；输出合计可能超过 BIGINT，不能按单行范围截断。均价 ROUND_HALF_UP 到1分，比例固定6位；负净额保留。订单计数/件数为整数。test_domain.py:480/512/534/559 分别覆盖半分、超默认精度、零分母和时区等价；退款未知 test_repair_refund_history.py:41/51/89/136。

结论：现有数值规则可采用，未知原因/完整度协议需补。 同意金额/比例字符串及精确判等；“禁止四舍五入掩盖差异”不能禁止约定的 HALF_UP：20001/2 分客单价应是 "10001"。比例仍保留尾零，如 "0.500000"。未知 null 不等于字段无权限时省略。

必须进入样例的区别：

  • 无支付订单：payment/refund 在完整现金窗内可为 "0"，count/units=0，均价/两率=null，channels/history 可为空。
  • 有零元 paid 订单：count=1，均价="0"，金额退款率=null；当前代码不要求 paid_minor>0，不能照搬 01 过滤。
  • 成功零额退款：当前存在事件即计入 cohort 退款订单数，可出现订单率="1.000000"、金额率="0.000000"。这是待业务确认的语义；冻结现状候选时必须忠实标注，不能悄改成“正额退款订单率”。
  • 单 SKU 原生金额已知，但混合 SKU 正额退款缺分摊：现金窗内只使 refund/net 未知；cohort 涉及该退款则两率未知。分别受窗与 visible 限制，不能整页都填 null，也不能补0。
  • 空日期不在 history 中；有事件日的另一个已知金额可为0。filter_missing 不是通用 coverage，不能证明数据“全店全量完整”。

最小方案与验证（I/R）：02 后续显式 coverage/unknown_reasons（授权后返回）与空结果结构，03 按字段类型/空值原因精确比较，SQL 同版用 NUMERIC/SUM 避免溢出，均价/比例用注册规则；容差不用于分金额和六位比率。fixtures.json 包含本轮可重跑合成对照，检查脚本只读替身验证当前计算，不证明未来 SQL 语法或执行器已通过。
