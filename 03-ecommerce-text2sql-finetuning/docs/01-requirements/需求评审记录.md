## 3. 第 1 轮问题（已在 §10 回答）

### Q1 数据来源与首版规模

**问题**：在无真实 CSV、无 EXTERNAL-GEN API 预算的前提下，第一版金标按哪条路径建设？

| 选项 | 内容 |
|---|---|
| A（建议） | 规则合成 + 人工审核的种子金标先行：先 20–30 题（01 12–18、02 8–12）跑通“问题→SQL→安全→沙箱→语义”闭环，再扩到 01 约 120–160、02 约 60–100；每题 2–3 组 fixture；EXTERNAL-GEN API 只做同义改写候选且另批预算；公开数据只做语法/鲁棒性辅助，不进业务金标 |
| B | 直接上 EXTERNAL-GEN API 批量生成 + 执行验证 + 人工抽检，首版 1–2K |
| C | 等真实 CSV/字段字典到位后再建，先只写规范 |

**建议理由**：数据是关键路径；A 不依赖外部预算，能先暴露 Schema/指标/判定器问题；B 依赖未批预算且 EXTERNAL-GEN 错误会污染金标；C 会停摆。  
**影响**：决定未来 2–3 周数据工作量、SFT 规模、GRPO 题库与评测可信度。  
**需要确认**：选 A/B/C；若 A，首版 20–30 与 seed 120–160/60–100 是否接受；审核人是谁（用户/01/02 owner）。

### Q2 v1 业务覆盖与优先级

**问题**：v1 是否按“01 主训 + 02 试点，02 全量待契约评审”推进？

| 选项 | 内容 |
|---|---|
| A（建议） | 双 profile 都写规范与评测；SFT 首轮以 01 `customer_self` 为主（契约、Schema、validator、executor 已实现且签收）；02 做 60–100 题试点评测/少量训练；02 全量待 `OPS-QUERY/METRIC` 与执行面联合评审 |
| B | 双 profile 等量建设，一次训练双 profile |
| C | 先只做 01，02 等 02 需求定稿后再立项 |

**建议理由**：01 是当前唯一可端到端核验的消费面；02 无执行接口，过早全量训练会把未批准口径固化进权重，返工成本高。A 仍交付 02 的规范、试点与评测，不是放弃 02。  
**影响**：数据量、评测复杂度、交付时间与“同一模型双 profile”的能力声明。  
**需要确认**：选 A/B/C；02 试点题量 60–100 是否接受；02 契约评审的时间窗。

### Q3 正确性判定与澄清口径

**问题**：标准答案与 GRPO 奖励的判定基准，是否采用“多 fixture 结果等价 + 契约/安全 + 响应类型”，而非 SQL 文本一致？缺时间窗/粒度/指标时澄清还是默认？

| 选项 | 内容 |
|---|---|
| A（建议） | 主判定=≥2 组有区分度 fixture 上执行候选 SQL 与金标 SQL，按声明规范化后结果多重集相等；同时通过 Schema/修订/参数/只读/资源/行数校验；query/clarify/unsupported/error 按标签与必填槽位判定；SQL 文本可不同，但必须满足指标口径断言；缺时间窗/粒度/口径时 `clarify`，不静默套 30 天；仅当 profile 文档明确允许默认时才用默认 |
| B | SQL AST/结构相似 + 执行 |
| C | 只判可执行且结果非空 |

**建议理由**：文本/AST 匹配会误杀等价写法；只判可执行会放过恒空、硬编码、错口径；A 可复核且能支撑 GRPO，但需要 fixture 工程与规范化规则。01 的 `date_range` 默认最近 30 天是固定操作层行为，不能直接等同于模型可静默默认。  
**影响**：金标制作成本、评测可信度、奖励实现与大量澄清样本的标签。  
**需要确认**：选 A/B/C；澄清优先还是允许 profile 默认；结果比较规则（多重集、NULL、金额、时区、排序）是否按 PRD 附录 A.4。
