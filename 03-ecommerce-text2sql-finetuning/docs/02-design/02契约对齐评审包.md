## 1. 结论摘要

1. **02 目前没有 SQL 面**：没有 query/validator/executor 模块；`GET /dashboard` 是内存快照上的确定性指标计算；`OPS-QUERY-v0.1` 是 6 行/9 个逻辑资源的草案，不是物理表。
2. **02 已有 8 个标量指标 + `channels[]`**：支付、退款、净额、支付订单数、支付件数、客单价、两个 cohort 退款率；时间锚点为 `paid_at`/`occurred_at`，`as_of = min(查询 as_of, watermark)`，时区 `Asia/Shanghai`，金额整数分，比率 6 位小数。
3. **01 与 02 不是同一口径**：01 用 `created_at` 圈单、退款按订单累计、会话时区 UTC；02 用支付/退款事件时间、退款现金期与 cohort 分离、日桶上海时区。同一句“11 月支付/退款”在两侧数值不同，不能共用标签。
4. **建议分阶段，不一步做 SQL**：
   - **阶段 A（现在可做）**：02 先确认指标/参数/`as_of`/维度/`cost.read` 契约；03 只生成“指标意图 + 参数 + 澄清/不支持”，由 02 固定工具执行，不生成 SQL。
   - **阶段 B（02 决定是否做）**：02 提供只读 SQL 执行面与 validator 后，03 再返回 SQL 候选；02 负责身份、权限、执行、限额与审计。
   - **阶段 C**：契约、fixture、权限反例通过后，才把 02 纳入正式训练和接入验收。
5. **不建议**把 `ops_*` 当已存在表训练，也不建议在 02 无执行面时声称“02 Text-to-SQL 已接通”。

### 2.2 02 实际输出的指标

| 指标字段 | 定义 | 时间锚点 | 空值/未知 |
|---|---|---|---|
| `payment_minor` | Σ `order.paid_minor`，`status=='paid'`，`paid_at ∈ [start,end)`，`paid_at <= visible` | 支付 `paid_at` | 无单→`"0"` |
| `paid_order_count` | 上述 cohort 的 distinct 订单数 | 支付 | 0 |
| `paid_units` | cohort 订单的 Σ `item.qty` | 支付 | 0 |
| `average_order_minor` | `payment / count`，6 位小数后转分 | 支付 | 分母 0→`null` |
| `refund_minor` | Σ `refund.amount_minor`，`succeeded`，`occurred_at ∈ [start,end)`，`<= visible` | 退款 `occurred_at` | 分摊缺失→`null` |
| `net_paid_minor` | `payment - refund`，可为负 | 混合：支付窗 − 退款窗 | 同上 |
| `cohort_refund_order_rate` | cohort 中有任意成功退款的 distinct 订单 / cohort 订单数；退款不限时点，只受 `visible` 截断 | cohort=`paid_at` 在窗内 | 分母 0→`null` |
| `cohort_refund_amount_rate` | cohort 已退款金额 / 原支付金额，6 位小数 | 同上 | `payment<=0`→`null` |
| `channels[]` | 按 `order.channel` 分组支付额 + 订单数；空白→`unknown` | 支付窗 | 缺失渠道归 `unknown` |

精度：金额 `ROUND_HALF_UP` 到分，比率 6 位小数（`domain.py:20-21`、`:118-121`、`:302-305`）。

### 2.3 02 的 `as_of`、时间与权限

- `visible = min(查询 as_of, watermark)`；支付与退款都必须 `<= visible`（`domain.py:253-261`、`service.py:175/187`）。
- 时区 `Asia/Shanghai`；窗口半开 `[start,end)`；`start>=end`→`invalid_window`；缺省 `end=now`、`start=end-30d`（`service.py:173-174`）。
- 每次导入是新的不可变 `(store_id, snapshot_id, revision)`；同修订内容不同→`revision_conflict`（`service.py:99-106`、`db.py:22-27`）。
- `cost.read`：`owner`/`operator` 有，`viewer` 只有 `metrics.read`；无能力时快照剔除 `cost_minor`/`variable_fee_minor`（`auth.py:13-18`、`service.py:131-143`、`:228-234`）。
- 即使有 `cost.read`，`contribution_profit_minor` 仍返回 `null` + `profit_missing_reason`（`service.py:228-232`）。
- 订单状态三值 `paid/unpaid/cancelled`；退款状态 `succeeded/pending/failed`；refund 要求原单 `paid`、`occurred_at>=paid_at`、成功退款累计 ≤ `paid_minor`（`domain.py:204-246`）。
- 快照没有：订单创建时间、`order_item_id`、商品原价/折扣、运费拆分、退货数量、仓库维度、访客/访问数据。

### 2.4 01 与 02 的关键差异

| 维度 | 01 customer_self | 02 operations_store | 后果 |
|---|---|---|---|
| 圈选 | `created_at` 建单窗 | `paid_at` 支付窗、`occurred_at` 退款窗 | 同一“11 月”不是同一批订单 |
| 退款 | 订单累计退款，归属建单窗，不可重放 | 现金期退款事件；cohort 退款另算 | `refunded_minor` ≠ `refund_minor` |
| as_of | 无；响应 `as_of` 是执行时刻 | 快照 watermark + 查询 `as_of` | 01 标签不稳定，02 可重放 |
| 时区 | 会话 `UTC` | `Asia/Shanghai` | 上海 00:00–08:00 日桶不同 |
| 状态 | 6 值 | 3 值 | 枚举不能同名直连 |
| 成本/渠道 | 不可见 | `cost.read`；`channel` | 01 不可答成本/渠道 |
| 粒度 | 订单含运费、行不含 | 订单金额等于行合计 | 行金额不可直接对齐 |

## 3. 需要 02 决定的问题

### Q-02-01 目标形态：先指标/意图，还是直接 SQL？

**现状**：02 无 SQL 执行面；FR-OPS-019 要“受控经营 Text-to-SQL”；DEP-03 明确 03 无当前协议。

**需 02 决定**：
- A. 第一阶段只做“指标意图 + 参数 + 澄清/不支持”，由 02 固定工具执行；
- B. 第一阶段就做只读 SQL 候选，02 提供 validator/executor；
- C. 暂不做 NL2SQL，只保留固定工具。

**03 建议**：A → B 分阶段。A 可立即验证“问题理解、指标选择、参数、澄清、权限拒绝”，不需要 02 先建 SQL 执行面；B 在 02 有 validator/executor/限额后再开。C 会让 FR-OPS-019 无法验收，但比“假装已接通”诚实。

**影响**：决定 02 训练样本形态、评测指标和 03 服务协议；B 需要 02 新增执行面与安全测试。

**样例**：
- 问“11 月支付金额和退款金额” → A：返回 `metric=intent(payment_minor/refund_minor)` + 参数，02 计算；B：返回 SQL 候选。
- 问“11 月退款率” → A：`cohort_refund_order_rate`/`cohort_refund_amount_rate` 二选一，歧义则澄清；B：SQL 候选 + 指标标签。

### Q-02-02 执行责任：谁校验、谁执行、谁审计？

**现状**：02 负责权限/执行/业务正确性（DEP-03）；03 只应返回候选；01 已有服务端身份绑定与只读执行器。

**需 02 决定**：
- 02 是否建设只读 validator/executor（语句、函数、字段、行数、超时、并发、`query_ref` 审计）？
- 是否允许 03 的离线沙箱只做评测，不接触 02 库？
- 越权/危险 SQL 由 02 拒绝并返回统一错误，还是由 03 预检后拒绝？

**03 建议**：02 独占执行与鉴权；03 只返回候选和参数；03 沙箱只用于离线 fixture 评测；02 记录 `query_ref`、调用方、范围、SQL 摘要、结果行数、耗时；03 永不接收 02 连接凭据。

**影响**：安全边界、审计责任、错误码归属；若让 03 执行，会违反“模型不持凭据、不执行”的边界。

**样例**：请求带 `consumer_profile=operations_store`、`snapshot_id`、`as_of`、`capabilities`；02 绑定 `store_id`/角色后执行，返回 `query_ref`；03 响应不含 DSN/密码。

### Q-02-03 `OPS-QUERY-v0.1` 的版本与资源子集

**现状**：6 行/9 个逻辑资源草案；`ops_traffic_period` 无来源；`ops_inventory` 无时点序列；`ops_order` 无创建时间；`ops_sales_period` 无实现；`ops_cost` 是有效段草案。

**需 02 决定**：
- v1 哪些资源是“契约资源”，哪些仍是示意？
- 是否提供机器可读 Schema（JSON/DDL）：字段类型、可空、枚举、关系、金额单位、时区、版本？
- 物理表/视图由 02 内部映射，03 是否只依赖逻辑名？

**03 建议**：v1 先冻结 7 个资源：`ops_order`、`ops_order_item`、`ops_payment`、`ops_refund`、`ops_sku`、`ops_cost`（受 `cost.read`）、`ops_inventory`（单时点）；`ops_sales_period`/`ops_traffic_period` 暂不进入契约（无来源/无实现）。Schema 用版本化 JSON + 字段字典，03 不猜物理表。

**影响**：训练样本的 Schema 输入、SQL 可表达范围、02 执行器实现量。

**样例**：`ops_order` v1 字段建议：`order_ref`、`paid_at`、`channel`、`payment_status`、`refund_status`、`paid_minor`、`currency`；不含姓名/电话/地址/顾客标识；`order_item` 含 `order_ref`、`sku_ref`、`qty`、`paid_minor`、`alloc_method`。

### Q-02-04 `OPS-METRIC-v0.1` 的字段、版本与响应

**现状**：8 个标量 + `channels[]` 已实现；`metric_revision` 只在方案计算常量里，dashboard 响应没有；指标名/字段名尚未作为跨项目契约。

**需 02 决定**：
- 是否把 8 个指标 + `channels[]` 冻结为 `OPS-METRIC-v0.1`？
- 指标 ID、中文名、公式、时间锚点、空值、精度、口径说明是否给机器可读定义？
- 响应是否必带 `metric_revision`、`calculation_revision`、`snapshot_id`、`as_of`？

**03 建议**：冻结 8 个指标为 v0.1；响应必带 `metric_revision`/`snapshot_id`/`as_of`；版本不匹配失败关闭；03 不新增“真实利润”公式，利润未知就返回未知；`channels[]` 作为维度结果，不另造指标。

**影响**：训练标签、奖励、评测口径；没有版本字段就无法证明 03 与 02 同口径。

**样例**：响应加 `"metric_revision":"OPS-METRIC-v0.1"`、`"snapshot_id":"..."`、`"as_of":"..."`；03 响应回显同一组字段。

### Q-02-05 `as_of`、快照与可重放

**现状**：02 `visible=min(query as_of, watermark)`；快照不可变 `(store_id,snapshot_id,revision)`；01 无 `as_of`，退款按查询时刻累计。

**需 02 决定**：
- 查询是否必须带 `snapshot_id` 或 `as_of`？缺省取最新 watermark 是否允许？
- 迟到数据/新 revision 如何影响旧标签？是否允许“按旧 as_of 重放”？
- 响应是否返回 `snapshot_id`/`revision`/`watermark`/`visible`？

**03 建议**：训练/评测样本必须绑定 `snapshot_id`+`as_of`+`metric_revision`；缺省只能用于交互，不得用于金标；旧 `as_of` 可重放；版本冲突失败关闭；01 标签额外绑定数据批次，不能只靠 `schema_digest`。

**影响**：标签稳定性、评测可复现、GRPO 奖励可重复。

**样例**：同一问题在 `as_of=2026-11-30` 与 `2026-12-10` 的退款额不同；金标必须写清 `as_of`，否则不可判分。

### Q-02-06 时间锚点与指标族：现金期、cohort、净额

**现状**：02 同时有现金期 `refund_minor` 与 cohort 退款率；`net_paid_minor` 可为负；退款可来自历史订单；01 的退款是订单累计、归属建单窗。

**需 02 决定**：
- v1 对外主指标是“现金期净实付”还是“支付 cohort”？
- 缺时间窗时澄清还是默认 30 天？默认是否写入契约？
- “本期退款”“退款率”“净额”是否必须限定指标族，禁止混用？

**03 建议**：把指标族写进 ID/标签：`cash_refund_minor`、`cohort_refund_order_rate`、`cohort_refund_amount_rate`、`net_paid_minor`；缺窗口澄清；默认 30 天只在 02 契约为交互场景明确允许时使用，金标不默认；禁止用现金期退款除本期支付冒充 cohort 率。

**影响**：大量样本的标签与澄清动作；混用会导致模型学到矛盾映射。

**样例**：问“11 月退款率” → 先澄清“现金期退款率（无此指标）/支付批次退款率（两个口径）”；不直接给一个数。

### Q-02-07 维度、粒度与可加性

**现状**：02 支持 store（绑定）、`channel`、`sku_id`、`start/end`；`channels[]` 是支付窗分组；`paid_units` 是订单行 qty；无仓库维度、无访客/访问数据；`ops_inventory` 单时点。

**需 02 决定**：
- v1 允许哪些分组维度：渠道、SKU、日/周桶？店铺是否只由会话绑定？
- 哪些指标可跨维度相加，哪些只能逐维报告？
- 空 `channel` 归 `unknown` 是否作为契约？行数/超时限额？

**03 建议**：v1 允许 store（绑定）、channel、SKU、Asia/Shanghai 日桶；禁止跨维度求和后当全店；`channels[]` 只报告不汇总；库存无仓/无时点序列，不承诺历史库存；流量/转化率暂不支持。

**影响**：SQL 的 GROUP BY/聚合合法性、fan-out 反例、评测维度。

**样例**：“按渠道支付额” → 02 `channels[]`；01 不支持（无 channel 列）。“按 SKU 支付件数” → 02 `paid_units` 需订单行；01 的 `ordered_qty` 不是支付件数，不能替换。

### Q-02-08 `cost.read`、成本与未知利润

**现状**：02 `cost.read` 控制 `cost_minor`/`variable_fee_minor` 投影；无能力时字段被剔除；即使有权限，贡献利润仍 `null` + 原因；01 无成本字段。

**需 02 决定**：
- 03 是否可见成本值？还是只可见 `cost.read` 能力布尔，由 02 执行成本查询？
- 成本/利润问题在无权限时返回 `unsupported` 还是 `error`？是否统一提示“能力不可用”？
- 训练数据是否允许包含成本数值/利润标签？

**03 建议**：03 不接收成本值；只接收 `cost.read` 能力声明；成本/利润由 02 受控执行；无权限统一“能力不可用”，不泄露字段存在；SFT/GRPO 样本不含真实成本值；利润未知不补 0，不训练模型自造公式。

**影响**：敏感字段边界、训练数据合规、评测可复现。

**样例**：请求 `capabilities:{"cost.read":false}`；问“11 月毛利” → `unsupported`/`clarify`（权限），不返回 SQL；有权限且成本完整时，02 返回 `contribution_profit_minor`，否则 `null` + 原因。

### Q-02-09 枚举、状态与退款映射

**现状**：02 订单 `paid/unpaid/cancelled`，退款 `succeeded/pending/failed`；01 订单 6 值（含 `completed/cancelled_refunded/closed_refunded`），退款以 `refund_execution` 行存在为成功。

**需 02 决定**：
- 跨项目统一枚举表，还是各 profile 独立、禁止同名直连？
- “已支付订单”“成功退款”“取消”在 02 的权威定义？
- 未知/空枚举如何表示？

**03 建议**：各 profile 独立枚举，附映射表；02 的 `paid` 只表示支付状态，不推断 `completed`；退款成功只认 `succeeded`；取消未付不计销售；未知枚举→`unsupported`/`clarify`，不猜。

**影响**：过滤器语义、样本标签、跨 profile 误用。

**样例**：01 的 `cancelled_refunded` 不能直接映射为 02 的 `cancelled`；02 的 `unpaid` 不是 01 的 `awaiting_payment` 的同义词，需显式映射。

### Q-02-10 参数、默认、澄清与限额

**现状**：02 dashboard 参数 `snapshot_id/start_at/end_at/sku_id/channel`；缺省 `end=now`、`start=end-30d`；`start>=end` 拒绝；03 的 SQL 输入要求 `request_id`、脱敏问题、profile、方言、Schema/指标版本、参数名/类型、能力限额（02 PRD §8.3 末段）。

**需 02 决定**：
- 03 请求的必填/可选字段、参数名/类型、默认值、时区格式；
- 缺窗口/歧义时 `clarify` 的槽位与话术；
- 行数、超时、并发、重试、幂等、限流；
- 是否要求 `request_id` 贯穿审计。

**03 建议**：必填 `request_id`、`consumer_profile`、`question`（脱敏）、`snapshot_id` 或 `as_of`、`start_at/end_at`、`schema_revision`、`metric_revision`、`capabilities`、`limits`；可选 `sku_id/channel`；缺窗口→`clarify`（不默认 30 天）；02 执行层做超时/行数/并发；03 不传 DSN/密码。

**影响**：服务协议、训练样本参数、错误码、SLA。

**样例**：请求缺 `start_at` → `kind=clarify`，`required_slots=["start_at","end_at"]`；`start>=end` → `kind=error`，`reason_code=invalid_window`。

### Q-02-11 响应契约、错误码与版本校验

**现状**：03 PRD 提议 `SQL-MODEL-v0.1`；02 需要 `query/clarify/unsupported/error`；02 现有 dashboard 响应不含 `metric_revision`；01 的 XCS-SQL-v0.1 是 01 侧草案。

**需 02 决定**：
- 采用统一 envelope 还是 02 自有 envelope + 03 适配？
- `kind` 四类、错误码、`required_slots`、`reason_code`、`query_ref`、`service_revision` 是否必填？
- 版本不匹配、超时、限流、空结果的返回方式；是否支持流式？

**03 建议**：v1 非流式 JSON；envelope 至少 `kind`、`schema_revision`、`metric_revision`、`snapshot_id`、`service_revision`、`parameters`、`sql`/`required_slots`/`reason_code`；执行结果另包 `query_ref`、`rows`、`row_count`、`as_of`；版本不匹配失败关闭；超时/限流有界重试，不静默降级。

**影响**：01/02 适配层、客户端错误处理、审计。

**样例**：`{"kind":"unsupported","reason_code":"cost_permission_denied","schema_revision":"OPS-QUERY-v0.1","metric_revision":"OPS-METRIC-v0.1"}`；不返回假 SQL。

### Q-02-12 精度、舍入与空值/0

**现状**：02 金额整数分、`ROUND_HALF_UP`、比率 6 位小数；`_amount(0)` 返回 `"0"`，指标字段不区分“无事件”与“0”；比率分母 0 返回 `null`；`net_paid_minor` 可为负。

**需 02 决定**：
- 输出类型：整数分字符串、比率字符串、负数表示；
- “无数据”和“真 0”是否在 API 层区分；空结果如何显示；
- 结果比较是否要求逐字段精确，还是允许容差。

**03 建议**：金额用整数分字符串（不用浮点）；比率 6 位小数字符串；负净额保留负号；未知用 `null` + `reason`；无数据与 0 在 `coverage`/`filter_missing` 中区分；评测逐字段精确，禁止四舍五入掩盖差异。

**影响**：评测判等、奖励、用户可见结果。

**样例**：`payment_minor:"60000"`、`net_paid_minor:"50000"`、`cohort_refund_order_rate:"0.666667"`；无支付时 `average_order_minor:null`，不是 `"0"`。

## 4. 同一问题的 01/02 对照样例（推演，未执行）

窗口 `W=[2026-11-01T00:00+08:00, 2026-12-01T00:00+08:00)`；示例数据：

| 订单 | 建单 | 支付 | 支付额（分） | 退款 |
|---|---|---|---|---|
| A | 10-31 23:50 | 11-01 00:05 | 10000 | 无 |
| B | 11-15 10:00 | 11-15 10:01 | 30000 | 11-20 成功退 10000 |
| C | 11-20 10:00 | 未支付，超时取消 | 0 | 无 |
| D | 11-25 09:00 | 11-25 09:01 | 20000 | 12-05 成功退 20000 |

01（`created_at` 圈单，12-10 查询）：支付 50000、退款 30000、净额 20000、已支付订单 2；退款包含窗口外发生的 D 退款；11-30 查询时退款只有 10000，净额 40000。

02（`as_of=2026-12-10`）：支付 60000、现金期退款 10000、净额 50000、支付订单 3；cohort 退款订单率 2/3=0.666667、金额率 30000/60000=0.500000。

| 问题 | 01 | 02 | 03 应做什么 |
|---|---|---|---|
| 11 月支付金额 | 50000 | 60000 | 按 profile 回答；跨 profile 不合并 |
| 11 月退款金额 | 30000（累计，含窗后） | 10000（现金期） | 指标 ID 必须带口径；不能同名 |
| 11 月净支付 | 20000 | 50000 | 同上；负值保留 |
| 11 月退款率 | 无定义 | 0.666667/0.500000 | 02 需澄清 order/amount；01 先 clarify 口径，有依据才 query，不一律 unsupported |
| 按渠道支付额 | 不支持 | `channels[]` | 01 `unsupported`；02 分组 |
| 11 月毛利 | 不支持 | 有 `cost.read` 才可；成本缺失→未知 | 01 `unsupported`；02 权限/未知 |

> 这些数字用于说明口径差异，不是 fixture，也不是金标；真正的 fixture 需 02/03 共同冻结快照与 `as_of`。
