## 1. 结论摘要

1. **01 已有一个可运行的 SQL 消费草案，但状态是“未联合批准”。** `contracts/sql_generation.json` 的 `status` 为 `01_consumer_draft_not_jointly_approved`，`external_validation` 明确“no real SQL service configured; project 03 not contacted”。03 不能把它当冻结契约。
2. **01 契约草案与当前代码字段不一致。** 草案示例用 `CS-QUERY-v0.1`/`CS-METRIC-v0.1`、`resources` 数组、`row_limit` 参数；当前代码是 `CS-QUERY-B2-v1`/`CS-METRIC-B2-v1`、`SCHEMA` 字典、`PARAMETERS` 只有 5 个名字且不含 `row_limit`。若 03 按草案做标签，会被 01 的 validator 拒绝或版本校验失败。
3. **01 的 `_sql_query` 只给 `start_at`/`end_at` 赋值。** 若候选 SQL 使用 `order_id`、`sku_id`、`status` 占位符，01 会走 `clarify`（`params - {"start_at","end_at"}`），即便 `PARAMETERS` 允许这些名字。模型要覆盖“我的某订单/某商品/某状态”类问题，必须先解决谁提供这些值。
4. **01 的 gateway 对 `project-sql` 协议要求响应自带 `service.model_identifier` 与 `service.revision`。** `deepseek-chat` 协议由 01 适配层注入 `service` 并补传输修订；`project-sql` 不注入。03 若走 `/generate`，必须返回完整 `service`，否则 01 直接拒绝。
5. **01 的 80 个获准 SQL 问题 + 至少 40 个反例尚未见到文件或清单。** 01 契约草案把它写成替换 API 的回归门槛；03 需要知道由谁提供、谁批准、在哪个库跑，否则无法设计交付包和验收证据。
