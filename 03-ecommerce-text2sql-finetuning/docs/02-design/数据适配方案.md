## 1. 目标与原则

1. 训练数据必须匹配获准的逻辑视图、字段、类型、关联、SQL 方言和指标口径，不能只把公开数据的表名替换成 `cs_*`/`ops_*`。
2. 公开数据只补通用 SQL 能力；业务能力必须由匹配 01/02 契约的数据训练和检验。
3. 先做 20–30 题工程小闭环，验证“问题 → SQL/澄清 → 安全校验 → 沙箱执行 → 结果断言”；通过后再扩量。
4. 每条样本绑定 profile、Schema 修订、指标修订、参数约束、fixture 和来源；缺一项即不可进入训练/评测。
5. 01/02 时间口径隔离：01 订单指标按 `created_at` 圈单；02 现金期按 `paid_at`/`occurred_at`，cohort 指标另算。不得混用。
6. 公开数据、业务适配、缺口候选、Codex 验证、业务签收是不同状态；状态不能跳级。

### 3.1 公开数据筛选标准（Codex 交付给 03 的输入）

- 许可证允许训练/评测/派生；记录数据集名、URL/commit、license、抓取时间。
- 有 schema DDL 与 question/SQL 对；SQL 方言可转换到 PostgreSQL；不含个人数据或可识别信息。
- 覆盖通用能力：过滤、聚合、分组、排序、多表 join、子查询、NULL、时间条件、除零/空结果。
- 不要求表名/字段与本项目一致；不允许把公开 schema 直接改名为 `cs_*`/`ops_*` 后当业务样本。
- 交付 manifest：样本数、schema 数、SQL 方言、许可、已知质量问题、建议用途（SFT/GRPO/评测）。
- 03 验收：抽查 10% SQL 可解析/可执行（在公开 schema 的隔离库），不通过则退回。

## 4. 01 customer_self 数据规范

### 4.1 逻辑资源与粒度

| 视图 | 粒度/主键 | 关键字段 | 允许关联 |
|---|---|---|---|
| `cs_order_self` | 一订单一行；`order_id` | `created_at`、`paid_at`、`trade_status`、`fulfillment_status`、`paid_minor`、`refunded_minor`、`net_paid_minor`、`currency` | 经 `order_id` 连 item/shipment |
| `cs_order_item_self` | 一订单行一行；`order_item_id` | `order_id`、`sku_id`、`product_name`、`ordered_qty`、`paid_goods_minor`、`refunded_qty`、`refunded_goods_minor`、`remaining_*` | 经 `order_id` 连 order；经 `sku_id` 连 product |
| `cs_shipment_self` | 一运单一行；`shipment_id` | `order_id`、`carrier`、`status`、`shipped_at`、`carrier_signed_at`、`tracking_updated_at` | 经 `order_id` 连 order |
| `cs_wallet_summary_self` | 一账户一行；`account_id` | `balance_minor`、`currency`、`status` | 不与其他视图按账户 join（无账户键） |
| `cs_wallet_entry_self` | 一流水一行；`entry_id` | `kind`、`amount_minor`、`sequence`、`balance_before_minor`、`balance_after_minor`、`occurred_at`、`currency` | 不与其他视图 join（无订单键） |
| `cs_product_public` | 一 SKU 一行；`sku_id` | `product_id`、`name`、`category`、`price_minor`、`available_qty`、`price_version`、`as_of` | 经 `sku_id` 连 item |

### 4.2 参数与约束

- 命名参数：`:start_at`、`:end_at`、`:order_id`、`:sku_id`、`:status`；SQL 中出现的参数集合必须与 `parameter_names` 完全一致；多传/少传均拒。
- `start_at`/`end_at` 必须成对、带时区；`start_at < end_at`；窗口 `[start_at,end_at)`；最长 366 天。
- 字符串枚举只能取 `ENUMS` 白名单（含 `paid/completed/cancelled_refunded/closed_refunded` 等）；数值字面量 ≤1e9；禁止 `SELECT *`（`count(*)` 除外）。
- 只读单语句；禁止 DDL/DML/系统目录/写函数/跨库；≤3 join、≤2 CTE、depth≤18、≤8192B、≤50 行。
- **节点白名单不含 `CASE`、`CAST`、`LIKE`、窗口函数、`abs/round/nullif/greatest/filter`**；`DATE_TRUNC` 只允许 `day/week/month`；不能按小时/季度分桶。
- **join 后直接 `SUM/AVG` 会被判 `ambiguous_grain`**；必须“单表/CTE 先聚合，再连接”，或 `IN (子查询)`；不要生成 `SELECT SUM(o.paid_minor) ... JOIN cs_order_item_self`。
- join 只允许等值且键限定在 `order_id`/`sku_id`/`shipment_id`；不得用 `OR`、函数、隐式转换构造关联。
- 输出列必须非空、唯一、小写蛇形；列名/别名不得含 `phone/address/street/password/secret/token/owner/staff/cost_`。
- 执行器会话时区为 **UTC**；`DATE_TRUNC('day', ...)` 得到 UTC 日，不是 Asia/Shanghai 日。01 的日/周桶若与业务日不一致，必须在问题/评测中标注，不能默认上海时区。
- 01 结果随退款落库而漂移（`refunded_minor` 是订单截至查询时刻的累计值，无 `as_of` 快照）；训练/评测 fixture 必须冻结数据库快照，不能用“今天查一次”的结果当永久金标。

### 4.3 指标口径

| 指标 | 粒度 | 时间锚 | 定义 | 未知/禁用 |
|---|---|---|---|---|
| `orders.count` | 一订单一计数 | `created_at` | 窗口内创建、`trade_status IN ('paid','completed','cancelled_refunded','closed_refunded')` 且 `paid_minor > 0` 的订单数 | 不得按订单行计数；不得把未支付/未支付取消计入 |
| `orders.paid_minor` | 订单 | `created_at` | 窗口内创建的上述已支付订单的原始 `paid_minor` 之和 | 不得用 `paid_at` 替代圈单窗口 |
| `orders.refunded_minor` | 订单 | `created_at` | 上述同一批订单的 `refunded_minor` 之和；是**截至查询时刻的累计退款**，与退款流水条数/退款发生时间无关 | 不得按退款事件时间重新圈单；问“本期退款”先澄清 scope |
| `orders.net_paid_minor` | 订单 | `created_at` | `paid_minor - refunded_minor`，同一批订单 | 不得对订单行金额求和后当订单金额 |

- 金额单位 CNY 分；输出为字符串整数分；不得用浮点。
- 退款/取消：`trade_status` 与 `fulfillment_status` 分别表达交易/履约；不得把“已取消未支付”计销售。
- **01 没有退款事件视图**：`refund_execution.refunded_at` 不在 6 个视图/GRANT 中；因此“本期退款/某月退款”在 01 口径下无法精确表达：先 `clarify` scope；“退款率”先 `clarify` 公式/范围，有可信依据才 query，不一律 unsupported；不得用 `refunded_minor` 冒充“本期退款”。
- 01 的固定查询层有“缺省近 30 天”行为；那是固定操作/服务层默认，不是模型可自行套用的默认。模型缺时间窗应 `clarify`，除非问题明确给出可解析窗口。
- 01 的固定读操作有 5 个：`orders.list`、`orders.detail`、`orders.summary`、`shipments.list`、`wallet.summary`；`orders.summary` 是 4 条注册指标的唯一实现入口。模型 SQL 面与固定操作面分开，不得把固定操作当模型已会。

### 4.5 01 禁用与未知

- 不提供成本、毛利、利润、供应商、员工、其他客户、手机号/地址等字段；出现即 `unsupported`，不得用相似字段替代。
- 不生成 `CASE`/`CAST`/`LIKE`/窗口函数/`abs/round/nullif` 等不在 01 validator 白名单的写法；不生成 join 后直接 `SUM` 的 SQL；`DATE_TRUNC` 只用 `day/week/month`。
- 不生成“本期退款/退款率”SQL；01 无退款事件视图。“本期退款/某月退款”先 `clarify` scope；“退款率”先 `clarify` 公式/范围，有可信依据才 query，不一律 unsupported。
- `cs_wallet_summary_self` 与 `cs_wallet_entry_self` 无订单键，不得臆造关联；余额与流水分别回答。
- `cs_product_public` 是公开商品快照，不代表用户购买价；不得把 `price_minor` 当实付；该视图无 owner 过滤（RLS 仅店铺/批次），不返回个人数据。
- 权限：模型不决定 `customer_self` 身份；SQL 不写 `owner_id`/`store_id` 等鉴权条件；执行器用会话变量+RLS 绑定。
- 01 执行器时区 UTC；日/周桶是 UTC 日，不是业务上海日。问题若明确“按北京时间日/周”，需在评测中标注 01 当前限制，不能静默当上海时区。

### 5.3 指标口径（草案）

| 指标 | 时间/口径 | 定义 | 未知/禁用 |
|---|---|---|---|
| `payment_minor` | `paid_at` 在 `[start,end)` 且 ≤`as_of` | 成功支付金额之和 | 失败/未支付不计；不得用订单创建时间 |
| `refund_minor` | 成功退款 `occurred_at` 在窗口且 ≤`as_of` | 成功退款金额之和（现金期） | 申请中/失败不计；不得用支付时间 |
| `net_paid_minor` | 上述两窗口 | `payment_minor - refund_minor`，可为负 | 不命名为会计收入/活动增量 |
| `paid_order_count` | `paid_at` 窗口 | 窗口内成功支付订单去重数 | 不同 SKU 订单数不可相加 |
| `cohort_refund_order_rate` | cohort=窗口内支付订单；退款截至 `as_of` | 有成功退款的 cohort 订单数 / cohort 订单数 | 分母为 0 返回 NULL/未知，不补 0 |
| `cohort_refund_amount_rate` | 同上 | cohort 退款金额 / cohort 支付金额 | 分母为 0 返回 NULL/未知；退款不折数量 |
| `paid_units` | cohort | cohort 订单的 `sum(item.qty)` | 不是退款数量；不得与订单数混用 |
| `average_order_minor` | cohort | `payment_minor / paid_order_count`，count=0 为 NULL | 不是客单价口径的跨期可比指标 |
| `channels[]` | cohort | 按 `channel` 分组的 `payment_minor`/`paid_order_count` | 渠道缺失归 `unknown`，不得丢行 |

- 时区 `Asia/Shanghai`；半开窗；`as_of` 与快照 `watermark` 取 `visible=min(as_of, watermark)` 截断；发生时间与入库/修订时间分列。
- 金额整数分字符串；比例定点；`ROUND_HALF_UP`；不混币。
- 成本/费用缺失时毛利/利润为未知，不补 0；`cost.read` 未授权时不得生成/返回成本字段。
- 退款分摊缺失时相关 SKU 退款指标未知；不得把订单级退款均摊成 SKU 退款。
- 02 现金期与 cohort 是两套分母，不得混算；不得把 `cohort_refund_*` 的分母换成现金期退款。
- 02 dashboard 当前返回 8 个标量指标 + `channels[]`；`OPS-METRIC-v0.1` 不是响应字段，只是草案标识。

### 5.5 02 禁用与未知

- 不生成写操作（发布、改价、退款、采购、排班）；不执行订单/退款/活动写。
- 不跨店；不绕过 `store_id` 范围；不把模型 WHERE 当鉴权。
- 缺 `cost.read` 不返回成本/毛利；缺成本不补 0；缺退款分摊不均摊；缺 `as_of` 不默认为当前时间（需契约依据）。
- 不把现金期退款率与 cohort 退款率混用；不把订单金额随订单行重复累计。

## 6. 01/02 口径隔离

| 维度 | 01 customer_self | 02 operations_store |
|---|---|---|
| 时间锚 | 订单指标 `created_at` | 现金期 `paid_at`/`occurred_at`；cohort 另算 |
| 会话时区 | 执行器 UTC；`DATE_TRUNC` 为 UTC 日 | `Asia/Shanghai`；日桶显式上海时区 |
| 退款 | 同一批 `created_at` 圈定订单的累计 `refunded_minor`，与流水条数/退款时间无关；无退款事件视图 | 现金期按退款事件时间；cohort 按支付批次订单的所有退款（截至 visible） |
| 可重放 | 无 `as_of` 快照；结果随退款落库漂移 | 快照 `snapshot_id/revision` + `as_of`/watermark |
| 金额粒度 | 订单/订单行分列 | 订单/订单行/支付/退款分列，先聚合再关联 |
| 默认值 | 模型缺时间窗→clarify；固定层 30 天不是模型默认 | 缺 `as_of`/窗口→clarify；默认需契约 |
| 权限 | `customer_self`，执行器绑定 | `operations_store`，店铺范围+字段权限 |
| 未知 | 无成本/利润字段 | 成本/分摊缺失→未知；`cost.read` |

**worked example（同一窗口，两套口径必然不同）**：

窗口 `W=[2026-11-01,2026-12-01)`，可见截至 `2026-12-10`：

| 订单 | 创建 | 支付 | 金额 | 退款 |
|---|---|---|---|---|
| A | 10-31 23:50 | 11-01 00:05 | 10000 | 无 |
| B | 11-15 10:00 | 11-15 10:01 | 30000 | 11-20 成功退 10000 |
| D | 11-20 | 11-20 | 20000 | 12-05 成功退 20000 |

- 01（`created_at ∈ W`，B+D）：`paid_minor=50000`，`refunded_minor=30000`（D 的 12-05 退款仍计入），`net=20000`；若在 11-30 查询，`refunded_minor=10000`、`net=40000`。**同一标签两个值**，因 01 无 `as_of`。
- 02 现金期（`paid_at/occurred_at ∈ W`）：支付 A+B+D=`60000`，退款只 B=`10000`，`net=50000`；A 是 10 月建单但 11 月支付，02 计入、01 不计入。
- 02 cohort（`paid_at ∈ W` = A/B/D，退款截至 12-10）：cohort 退款 `30000`，`cohort_refund_order_rate=2/3`，`cohort_refund_amount_rate=30000/60000=0.5`。

因此：“11 月卖了多少/退了多少”在 01/02 下答案不同；样本必须绑定 profile 与口径，不能用一套 SQL 换表名。

**硬规则**：

1. 样本必须绑定 `profile` + `schema_revision` + `metric_revision`；三者任一不匹配即拒绝。
2. 01 模板不得用于 02，02 模板不得用于 01；不得共用 SQL 模板只换表名。
3. 交叉反例必须进评测：把 01 的 `created_at` 口径 SQL 放到 02 题、把 02 的 `paid_at` 口径 SQL 放到 01 题，均应判错。
4. 02 试点样本标记 `pilot_only=true`，不进入正式 SFT/GRPO，直到契约评审通过。

## 7. 来源与构建流程

### 7.1 公开数据（Codex 筛选 → 03 使用）

1. Codex 交付 manifest + 样本 + schema；03 抽查许可、SQL 方言、可解析性。
2. 03 只把公开数据用于通用 SQL 能力（语法、结构、方言转换），不映射 `cs_*`/`ops_*` 业务表。
3. 公开数据样本带 `source_type=public-general`，不进入业务测试集；不与业务样本混算业务准确率。
4. 公开数据中的 SQL 方言（SQLite/MySQL）需转换为 PostgreSQL 并重验；转换脚本/规则记录版本。

### 7.2 业务适配（03 构建）

1. 从 01/02 契约生成问题族模板；每个模板绑定资源、字段、参数、指标、期望响应类型。
2. 为每题写金标 SQL（命名参数）或澄清槽位；金标 SQL 必须过对应 validator（01）或 02 契约校验（待建）。
3. 为每题准备 ≥2 组 fixture：一组正例、一组边界/反例；fixture 可重建、确定性、无真实个人信息。
4. 生成结果断言：排序、重复行、NULL、金额精度、时区、时间边界、退款、权限边界。
5. 03 自检：SQL 可解析、可执行、结果断言通过、与问题语义一致；记录自检人/时间。
6. 交 Codex 独立检验；通过后状态 `codex-verified`；业务签收后 `business-approved`。

### 7.3 缺口生成（03 → Codex）

1. 维护覆盖矩阵：问题族 × 资源 × 指标 × 期望类型 × 难度；标出缺口。
2. 03 只对缺口生成候选，标 `gap-candidate`；候选必须绑定契约修订和 fixture。
3. 候选交 Codex 独立检验；Codex 不通过则退回，不进入训练。
4. 候选通过后仍需业务签收（01/02）才成为业务金标；Codex 检验不替代业务签收。

### 7.4 EXTERNAL-GEN（可选）

- 只生成候选/同义改写，不产生软标签、不参与损失、不作为奖励模型；调用预算另批。
- 生成内容必须人工/Codex 复核；不得直接进训练集。
- 记录供应商、模型版本、调用时间、prompt 版本、费用；密钥不落盘、不进样本。

## 9. Fixture 与结果断言规范

### 9.1 Fixture

- 每题 ≥2 组 fixture：A 正例（有区分度、非空）、B 边界/反例（空结果、NULL、重复、退款、跨窗、权限拒绝）。
- 确定性：固定 seed、固定时间、固定金额；不依赖当前时钟/随机/外部服务。
- 隔离：03 独立 PostgreSQL 沙箱；不连接 01/02 应用库/联调演示库；凭据只给执行器。
- 可重建：fixture 种子/SQL/初始化命令/期望结果哈希；不得只存结果 CSV 不存种子。
- 区分度：正确 SQL 与错误 SQL（恒空、漏过滤、错 join、错口径）必须产生不同结果；不能“都空”。

### 9.2 结果比较

| 维度 | 规则 |
|---|---|
| 排序 | 只有金标 SQL/问题明确排序时才比较顺序；否则比较多重集 |
| 重复行 | 按多重集计数；`DISTINCT` 误用/漏用必须暴露 |
| NULL | NULL 与 0 不同；`COALESCE` 仅在金标明确时允许 |
| 金额 | 整数分精确比较；不使用浮点；字符串/整数表示归一化 |
| 时间 | `Asia/Shanghai`；半开窗；边界值（start/end）必须有用例 |
| 退款 | 01 与 02 分别验证；不得把退款金额折数量；01 订单净额非负，02 现金期净额可为负 |
| 关联 | fan-out/重复计数反例：订单×订单行、订单×退款、订单×运单 |
| 权限 | 越权/跨店/敏感字段必须 `unsupported`/`error`，不得返回数据 |
| 空结果 | 空结果是合法结果；但必须与“错误 SQL 恰好为空”区分（用正例 fixture） |

### 9.3 响应类型判定

- `query`：SQL 可解析、过 validator/契约、执行成功、结果断言通过。
- `clarify`：缺必要条件/歧义；`clarify_slots` 与金标槽位集合一致；不得执行 SQL。
- `unsupported`：越权/不支持的能力/字段/写操作；原因码匹配。
- `error`：模型/服务/执行错误；不得把错误伪装成空结果或澄清。

## 10. 切分与防泄漏

1. 先按 `template_id`/`split_group` 分组，再分 `train/dev/test`；同组不跨集。
2. 同义改写（`paraphrase_of`）与种子同组；改写不得跨集。
3. 相近 SQL（同一模板/同一资源组合）同组；避免测试集出现训练模板的只换词版本。
4. 公开数据按数据集/来源分组；同一数据集不跨 train/test。
5. 02 试点样本单独 `pilot` 分组，不混入 01 训练/测试。
6. 测试集冻结：版本、哈希、样本 ID 列表；训练/调参不得读取测试答案；GRPO 奖励不得用测试答案。
7. Codex 独立留出集：03 不见答案；用于最终验收；不得用其调参。

| 阶段 | 规模（建议） | 用途 | 出口 |
|---|---|---|---|
| 工程小闭环 | 当前 25 分支（全 01；S06C/S06Q 分开）；目标态 20–30 题（01 为主，含 5–8 题 02 pilot） | 验证问题→SQL→安全→沙箱→断言 | 全链路可复核；错误分类清楚 |

- `fixtures/`：种子 SQL/快照/初始化命令/期望结果。

- `repro/`：执行命令、环境版本、随机种子、结果指纹。

- 名称/版本/日期/所有者；来源与许可；样本数与分布；问题族覆盖；Schema/指标修订；切分与防泄漏；fixture 与断言；审核状态；已知偏差/限制；未覆盖项。
